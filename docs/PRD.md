# PRD — GT7 MOTOR CMS

- **ผลิตภัณฑ์:** GT7 MOTOR CMS
- **ประเภท:** ระบบจัดการเนื้อหาสำหรับ landing page
- **สถานะ:** PRD เริ่มต้น อ้างอิงพฤติกรรมและ schema ปัจจุบันของโปรเจกต์
- **ผู้เกี่ยวข้องหลัก:** เจ้าของ/ผู้ดูแลเว็บไซต์, ผู้พัฒนา

## 1. ภาพรวม

GT7 MOTOR CMS เป็นระบบจัดการเนื้อหาของหน้า Landing Page โดยให้ผู้ดูแลที่ได้รับอนุญาตแก้ไข header, เนื้อหาหลัก และ footer ผ่านหน้าแอดมิน จากนั้นบันทึกและเผยแพร่ไปยังหน้าเว็บที่เชื่อมกับ Supabase

เอกสารนี้อธิบายขอบเขตที่มีอยู่จริงในโค้ดปัจจุบัน พร้อมเกณฑ์การยอมรับสำหรับพฤติกรรมหลัก ข้อเสนอที่ยังไม่ยืนยันจะแยกไว้ในหัวข้อแนวทางพัฒนาต่อไป

## 2. ปัญหาและโอกาส

การแก้ไขเนื้อหาหน้าเว็บโดยตรงผ่านโค้ดทำให้ผู้ดูแลต้องพึ่งพานักพัฒนาและกระบวนการ deploy ระบบ CMS จึงควรให้ผู้ดูแลเปลี่ยนเนื้อหาพื้นฐานและเผยแพร่ได้ด้วยตนเอง โดยยังคงควบคุมสิทธิ์และเก็บข้อมูลในฐานข้อมูลส่วนกลาง

## 3. เป้าหมาย

1. ให้ผู้ดูแลที่ได้รับสิทธิ์เข้าสู่ระบบและแก้ไขส่วนต่าง ๆ ของ landing page ได้
2. เผยแพร่เนื้อหาที่บันทึกไปยังหน้า public โดยไม่ต้อง build แอปใหม่
3. จำกัดการเขียนข้อมูลและการจัดการรูปภาพไว้เฉพาะผู้ดูแล
4. แสดงข้อผิดพลาดที่เข้าใจได้เมื่อเชื่อมต่อฐานข้อมูลหรือบันทึกไม่สำเร็จ

### ไม่ใช่เป้าหมายของรุ่นปัจจุบัน

- ระบบหลายเว็บไซต์หรือหลาย tenant
- ระบบ workflow อนุมัติเนื้อหาและบทบาทบรรณาธิการหลายระดับ
- การตั้งเวลาเผยแพร่, draft/history หรือ rollback เนื้อหา
- การจัดการ SEO แบบครบถ้วน (เมนู SEO ยังระบุว่าเร็ว ๆ นี้)
- ระบบวิเคราะห์ผู้เข้าชมและ A/B testing

## 4. ผู้ใช้และสิทธิ์

### ผู้ดูแลเว็บไซต์ (Admin)

- เข้าสู่ระบบด้วยบัญชี Supabase Auth
- เข้าถึงหน้า `/admin` ได้เมื่อ `app_metadata.role` เท่ากับ `admin`
- จัดการ header, body, footer และอัปโหลดไฟล์รูป
- ออกจากระบบได้

### ผู้เข้าชมเว็บไซต์ (Public visitor)

- เปิดดู landing page โดยไม่ต้องเข้าสู่ระบบ
- อ่านเนื้อหาที่เผยแพร่แล้วและใช้ลิงก์/ปุ่มที่ผู้ดูแลกำหนด
- ไม่มีสิทธิ์เขียนข้อมูล CMS หรือจัดการไฟล์

## 5. ขอบเขตผลิตภัณฑ์

### 5.1 การเข้าสู่ระบบและการควบคุมสิทธิ์

- หน้า `/admin/login` รับอีเมลและรหัสผ่านผ่าน Supabase Auth
- ทุกเส้นทาง `/admin/:path*` ต้องตรวจ session และ role
- หากยังไม่เข้าสู่ระบบหรือไม่มี role ที่กำหนด ให้ไปหน้าเข้าสู่ระบบ
- หาก admin เปิดหน้า login ให้ไปหน้าแอดมิน
- Server Actions และนโยบาย RLS ต้องตรวจสิทธิ์ซ้ำก่อนเขียนข้อมูล

**เกณฑ์การยอมรับ**

- บัญชีที่มี `app_metadata.role = admin` เข้าหน้าแอดมินได้
- บัญชีที่ไม่มี role เป็น admin ถูกปฏิเสธ และไม่สามารถบันทึกข้อมูล CMS ได้
- การออกจากระบบทำให้ session ใช้งานต่อกับหน้าแอดมินไม่ได้
- ข้อความผิดพลาดจากการเข้าสู่ระบบไม่เปิดเผยรายละเอียดภายในระบบ

### 5.2 Dashboard แอดมิน

- แสดงลิงก์ไปยังตัวแก้ไข header/navbar, body และ footer
- แสดงสถานะข้อมูลที่บันทึกไว้หรือแจ้งว่าเป็นข้อมูลตัวอย่าง
- แสดงข้อผิดพลาดเมื่อโหลดข้อมูลจาก Supabase ไม่สำเร็จ

### 5.3 Header / Navbar

- ตั้งค่ารูปแบบโลโก้เป็นข้อความหรือรูปภาพ พร้อมสีพื้นหลัง
- ตั้งค่าการทำงานของโลโก้และปุ่มเข้าสู่ระบบเป็นไม่ทำอะไร, ไปยัง section หรือเปิดลิงก์
- ตั้งค่าปุ่มนำทางได้สูงสุด 8 ปุ่ม
- ปุ่มนำทางรองรับ action และรายการย่อยแบบ dropdown; รายการย่อยไม่รองรับ dropdown ซ้อน
- กำหนด label, URL/section, สี, เส้นขอบ และการเปิดลิงก์แท็บใหม่ตามชนิดรายการ

**เกณฑ์การยอมรับ**

- บันทึกแล้ว header public แสดงค่าล่าสุดและเรียงลำดับตามที่กำหนด
- ระบบปฏิเสธรายการนำทางเกิน 8 ปุ่ม
- ลิงก์ภายในอ้างถึง anchor ของ body section ที่มีอยู่

### 5.4 Body sections

- เพิ่ม แก้ไข ลบ และเรียงลำดับ section ของหน้า
- ตั้งชื่อ anchor ที่ไม่ซ้ำและประกอบด้วยตัวอักษรอังกฤษ ตัวเลข หรือขีดกลาง
- รองรับ template: `hero-c`, `hero-l`, `ti-l`, `ti-r`, `cards`, `gal3`, `gal2`, `cta`, `txt`
- กำหนดสีพื้นหลัง การจัดแนว หัวข้อ ข้อความ รูปภาพ และปุ่มตามข้อมูลของแต่ละ section
- section แบบ cards รองรับการ์ดสูงสุด 6 ใบ
- section แบบ gallery รองรับรูปสูงสุด 6 รูป

**เกณฑ์การยอมรับ**

- section แสดงผลตาม template และลำดับที่บันทึกไว้
- anchor ที่ซ้ำในหน้าเดียวกันไม่สามารถบันทึกได้ และแสดงข้อผิดพลาดที่ผู้ดูแลเข้าใจได้
- ลิงก์จากเมนูที่อ้าง anchor จะไปยัง section เป้าหมาย

### 5.5 Footer

- ตั้งค่าสีพื้นหลัง รูปพื้นหลัง และความทึบ overlay
- รองรับคอลัมน์ได้สูงสุด 4 คอลัมน์
- ชนิดคอลัมน์ที่รองรับ: logo, links, mapphone, phone, map, email และ line
- ตั้งค่าลิงก์และข้อมูลติดต่อ พร้อมปุ่มที่เกี่ยวข้องตามชนิดคอลัมน์

**เกณฑ์การยอมรับ**

- Footer แสดงคอลัมน์และข้อมูลตามลำดับที่บันทึก
- ระบบไม่ยอมรับตำแหน่งคอลัมน์นอกช่วง 1–4
- ลิงก์และปุ่มแสดงปลายทางที่ผู้ดูแลตั้งค่า

### 5.6 รูปภาพ

- อัปโหลดรูปไปยัง Supabase Storage bucket `site-assets`
- การจัดการไฟล์ต้องผ่าน policy สำหรับ admin
- ส่วน public อ่านไฟล์จาก bucket ตาม URL ที่บันทึกในเนื้อหา

**เกณฑ์การยอมรับ**

- Admin อัปโหลดและนำ URL รูปไปใช้กับเนื้อหาได้
- ผู้ใช้ที่ไม่มีสิทธิ์ admin ไม่สามารถเขียนหรือลบไฟล์ใน bucket ได้
- เมื่ออัปโหลดไม่สำเร็จ ตัวแก้ไขต้องแจ้งข้อผิดพลาดและไม่บันทึกผลสำเร็จเท็จ

### 5.7 การบันทึกและเผยแพร่

- Header, body และ footer บันทึกผ่าน RPC แยกกัน
- แต่ละ RPC ตรวจสิทธิ์ admin และบันทึกการเปลี่ยนแปลงแบบ atomic
- หลังบันทึกสำเร็จให้ revalidate หน้า `/` เพื่อให้ผู้เข้าชมเห็นเนื้อหาใหม่
- หน้า public ใช้การแคชและมี revalidation interval 24 ชั่วโมงเป็น safety net
- หากไม่มีข้อมูล public ให้แสดงสถานะว่างแทนการทำให้หน้าเว็บล้มเหลว

**เกณฑ์การยอมรับ**

- เมื่อบันทึกสำเร็จ หน้า public แสดงข้อมูลใหม่โดยไม่ต้อง build ใหม่
- เมื่อบันทึกล้มเหลว ผู้ดูแลได้รับข้อผิดพลาดและไม่มีการแจ้งว่าสำเร็จ
- RPC ไม่ทิ้งข้อมูลครึ่งชุดเมื่อคำสั่งใน transaction เกิดข้อผิดพลาด

## 6. ข้อกำหนดข้อมูลและธุรกิจ

- ประเภทเนื้อหาแบ่งเป็น header, body และ footer
- ข้อมูล section อ้างอิง `site_sections` และการลบ parent ต้องจัดการ child records ตาม foreign key
- ชื่อ anchor ต้องไม่ซ้ำภายใน body page เดียวกัน
- ลำดับปุ่มนำทางไม่เกิน 8; ลำดับการ์ดและรูป gallery ไม่เกิน 6 ต่อ section
- จำนวนคอลัมน์ footer ไม่เกิน 4
- ค่า action และ template ต้องเป็นค่าที่ schema อนุญาต
- Role admin เก็บใน `auth.users.raw_app_meta_data` ไม่ใช้ `user_metadata` ที่ผู้ใช้แก้เองได้
- ตารางเนื้อหาเปิดอ่าน public ผ่าน RLS; การเขียนจำกัดด้วย `is_admin()`

## 7. ข้อกำหนดที่ไม่ใช่ฟังก์ชัน

### ความปลอดภัย

- ใช้ Supabase anon key สำหรับ public client; ห้ามส่ง service-role key ไปยัง browser
- ทุกการเขียนต้องผ่านการตรวจ role ฝั่งเซิร์ฟเวอร์และ RLS ฝั่งฐานข้อมูล
- คุกกี้ auth ต้องอ่านและเขียนผ่าน Supabase SSR cookie methods
- ห้ามบันทึกรหัสผ่านหรือ secret ลง log, source code หรือเอกสาร

### ความน่าเชื่อถือและประสิทธิภาพ

- ข้อมูล public ต้องแสดงได้โดยไม่ต้องมี session ของ admin
- การเขียนข้อมูลแต่ละส่วนต้อง atomic
- หน้า public ใช้ cache/revalidation เพื่อลดการอ่านฐานข้อมูลซ้ำ
- ความล้มเหลวของ Supabase ต้องไม่ถูกแสดงเป็นผลสำเร็จ

### การดูแลรักษา

- schema change ใหม่ต้องเพิ่มเป็น migration ใน `supabase/migrations/`
- ต้องสามารถตรวจ build ด้วย `npm run build` และ lint ด้วย `npm run lint`
- เอกสารการติดตั้งและ deploy อยู่ใน README

### การเข้าถึงและอุปกรณ์

- **ข้อเสนอให้ยืนยันก่อนเปิดใช้งานจริง:** ตรวจการใช้งาน keyboard, screen reader, contrast และ viewport มือถือ/แท็บเล็ตให้ครบทุก editor
- พฤติกรรม responsive และเป้าหมาย WCAG ยังไม่ได้ยืนยันจาก requirement ของเจ้าของผลิตภัณฑ์

## 8. เส้นทางผู้ใช้หลัก

### ผู้ดูแลเผยแพร่การแก้ไข

1. เปิด `/admin/login` และเข้าสู่ระบบ
2. เลือก header, body หรือ footer จาก dashboard
3. แก้ไขข้อมูลและอัปโหลดรูปหากจำเป็น
4. กดบันทึกและเผยแพร่
5. ระบบตรวจสิทธิ์ บันทึกผ่าน RPC และ revalidate หน้า public
6. เปิดหน้าแรกเพื่อตรวจผลลัพธ์

### ผู้เข้าชมดูหน้าเว็บ

1. เปิดหน้าแรกโดยไม่ต้องเข้าสู่ระบบ
2. ระบบโหลดเนื้อหาที่อ่านได้จาก Supabase
3. แสดง header, sections และ footer ที่มีข้อมูล
4. ผู้เข้าชมใช้เมนูและปุ่มเพื่อนำทางไปยัง section หรือลิงก์ภายนอก

## 9. ตัวชี้วัดความสำเร็จ

ตัวเลขเป้าหมายยังต้องตกลงกับเจ้าของผลิตภัณฑ์ ตัวชี้วัดที่แนะนำ:

- อัตราการบันทึกสำเร็จ แยกตาม header/body/footer
- จำนวนและประเภทข้อผิดพลาดจากการบันทึกหรืออัปโหลด
- เวลาตั้งแต่กดบันทึกจนหน้า public แสดงค่าล่าสุด
- อัตราการเข้าสู่ระบบสำเร็จและจำนวนการปฏิเสธสิทธิ์ที่ไม่คาดหมาย
- ผลตรวจการใช้งานบนมือถือและด้วย keyboard/screen reader

## 10. ความเสี่ยงและกรณีขอบ

- Environment variables ไม่ตรงกับ Supabase project ที่ใช้รัน migration
- Schema หรือ RPC ยังไม่ได้ apply ทำให้โหลดหรือบันทึกข้อมูลไม่ได้
- ข้อมูลเก่าอาจอ้าง section, URL หรือไฟล์ที่ถูกลบแล้ว
- การแก้ไขพร้อมกันจากหลาย session อาจเขียนทับข้อมูลล่าสุด เนื่องจากยังไม่มี version conflict handling
- การแก้ app metadata ต้องออก session ใหม่เพื่อให้ claim ใน token อัปเดต
- ลิงก์ที่ผู้ดูแลใส่อาจผิดรูปแบบหรือชี้ไปยังปลายทางที่ไม่ปลอดภัย; validation policy ยังต้องกำหนด

## 11. ข้อเสนอสำหรับรุ่นถัดไป (ยังไม่อยู่ในขอบเขตปัจจุบัน)

รายการต่อไปนี้ต้องจัดลำดับและยืนยันก่อนนำไปพัฒนา:

1. Preview draft ก่อนเผยแพร่
2. ประวัติ revision และ rollback
3. ตั้งเวลาเผยแพร่และ workflow อนุมัติ
4. กำหนดสิทธิ์ editor/viewer หลายระดับ
5. ฟอร์มจัดการ SEO และ social sharing metadata
6. ตรวจชนิด/ขนาดไฟล์และยืนยันก่อนแทนที่หรือลบรูป
7. Conflict detection เมื่อผู้ดูแลหลายคนแก้ข้อมูลพร้อมกัน
8. กำหนดเป้าหมายด้าน responsive, accessibility และ performance ที่วัดผลได้

## 12. คำถามที่ต้องยืนยันกับเจ้าของผลิตภัณฑ์

- มีผู้ดูแลกี่คน และต้องมี role นอกเหนือจาก admin หรือไม่?
- ต้องการบันทึกเป็น draft ก่อนเผยแพร่หรือให้การบันทึกเผยแพร่ทันที?
- ต้องเก็บประวัติและคืนค่าเนื้อหาเวอร์ชันก่อนหน้าหรือไม่?
- ต้องการ SEO fields ใดบ้าง เช่น title, description, canonical และ social image?
